# Hardware Inventory Ingest

How a hardware inventory kept as markdown tables becomes queryable DCIM data,
without the prose moving anywhere. The modeling decisions behind it are in
[hardware-modeling.md](hardware-modeling.md); this page is the pipeline.

## Shape of the pipeline

```text
inventory tables (markdown, hand-authored)
  -> converter script  -> inventory.seed.yml  (generated, committed)
    -> INT_HOMELAB_HARDWARE
      -> roles/nautobot/tasks/seed_bundle.yml
        -> nautobot_seed.json  (hardware_devices + hardware_modules)
          -> "Seed Hardware Inventory" Job
            -> Nautobot Devices and Modules
```

The markdown stays the authoring surface. Only the **structured** columns are
rendered into the generated YAML; the free-text notes column is deliberately
left behind, because DCIM models none of it and absorbing it would destroy the
most useful content in the source.

## Why the generated file is committed

A generated artifact that is not committed is regenerated by whoever runs the
converge, which makes the ingest depend on a working checkout of the authoring
repo at converge time. Committing it makes the exact input reviewable in a
diff, and lets CI assert the generated file still matches its source. The
staleness check is not optional: a generated file that silently lags its source
is invisible by construction, and Nautobot would keep serving the old picture
with nothing indicating it.

## Why the seed job is a plain Job, not a DiffSync DataSource

Every other seed job in this role is a `nautobot_ssot` `DataSource`. The
hardware one is not, and the reason is structural rather than stylistic:
`Module` and `ModuleBay` both declare `natural_key_field_names = ["pk"]`,
because their parentage is recursive. `nautobot_ssot`'s contrib models resolve
foreign keys through the related object's natural key, so a DiffSync attribute
for `parent_module_bay` would have to carry a primary key — not stable between
environments, and not present in the source data at all.

An idempotent ORM upsert keyed on the unique `asset_tag` gives the same
additive contract with none of that. What is given up is DiffSync's diff
report; the job's dry-run flag covers the "what would this change" case.

## Placement rules the job enforces

| Source row | Result |
| --- | --- |
| Chassis category, location is a bin | `Device`, named by its hardware ID |
| Chassis category, location names a host | left alone — the rack-server seed owns that Device |
| Component, location names an existing Device | `Module` in a `ModuleBay` on it, `location` cleared |
| Component, location is a bin | `Module` at that `Location`, no parent bay |
| Component naming a Device that does not exist | `Module` at the stated location, **with a warning** |

The last row is the one worth stating plainly: the job never creates a
placeholder chassis to hang an orphan component off. A synthetic Device is
indistinguishable from a real one forever afterwards, and every later query,
export and drift report inherits the lie. Filing the part where the source says
it is, and logging that the chassis is missing, keeps the gap visible.

`location` and `parent_module_bay` are mutually exclusive on `Module` by model
constraint, so the job sets one and explicitly clears the other on every write
rather than leaving whichever value happened to be there.

## Additive, like every other seed

Nothing in this path deletes. A row that disappears from the source leaves its
Nautobot object alone, because Device Onboarding, another seed job, or a human
may own it. Removing hardware from Nautobot is a deliberate act, not a
side effect of an edit to a markdown table.

## Ordering

The hardware job runs **after** the DCIM seed. A component installed in a
chassis needs that chassis to exist as a Device first; run it earlier and every
installed part is filed as a spare with a warning, which is a correct-looking
result that is entirely wrong.

## Verifying an ingest

1. Run the job with its dry-run flag first and read the reported counts. They
   should match the source row counts split by device/module.
2. After a committing run, confirm the totals in Nautobot: the count of
   `Device` plus `Module` objects carrying an asset tag should equal the number
   of source rows, less the chassis rows the rack-server seed owns.
3. Check the job log for "no such Device" warnings. Each one is either a
   chassis that has not been modelled yet or a typo in the source location
   column — both are real findings, not noise to filter out.
